## RESUMEN

El concepto de base de datos (*data base*) deriva de los primeros sistemas en línea (*on-line*) militares, y originalmente no estaba asociado con las tecnologías específicas de los modernos sistemas de gestión de bases de datos (*Data Base Management Systems, DBMS*). Si bien la idea de una base de datos integrada, o "cubo de hechos" (*bucket of facts*), se difundió en los círculos corporativos de procesamiento de datos y gestión durante la década de 1960, rara vez se materializó en la práctica. Los paquetes de procesamiento de archivos (*file-processing packages*) estuvieron entre los primeros en distribuirse como productos con soporte técnico, pero solo a finales de la década de 1960 comenzaron a denominarse "sistemas de gestión de bases de datos" (*data base management systems*), en gran medida gracias a las acciones del Grupo de Trabajo sobre Bases de Datos (*Data Base Task Group, DBTG*) del Comité sobre Lenguajes de Sistemas de Datos (*Committee on Data Systems Languages, CODASYL*). A medida que el concepto de DBMS se difundió, la base de datos en sí misma fue efectivamente redefinida como el contenido informativo de un DBMS comercializado. A lo largo de este proceso, las descripciones gerenciales de la base de datos como un repositorio flexible e integrado para todos los datos corporativos contrastaron marcadamente con la naturaleza útil pero limitada de los sistemas reales.¹

## 1. INTRODUCCIÓN

El Sistema de Gestión de Bases de Datos (*Data Base Management System, DBMS*) constituye el fundamento de casi todos los sistemas modernos de información empresarial. Prácticamente todos los procesos administrativos en los ámbitos empresarial, científico o gubernamental dependen de una base de datos. El auge de Internet solo ha acelerado esta tendencia: hoy en día, una ráfaga de transacciones de bases de datos impulsa cada actualización de contenido en un sitio web importante, una búsqueda bibliográfica o una experiencia de compra en línea. Sin embargo, muy pocas investigaciones abordan la historia de esta tecnología vital, ni la de las ideas que la sustentan. Sabemos poco sobre su evolución técnica, y aún menos sobre cómo ha cambiado su uso a lo largo del tiempo.²

Un sistema de gestión de bases de datos es una pieza muy compleja de software de sistema. Un único DBMS puede gestionar múltiples bases de datos, cada una de las cuales suele estar compuesta por muchas tablas diferentes llenas de datos. El DBMS incluye mecanismos para que los programas de aplicación almacenen, recuperen y modifiquen estos datos, y también permite a las personas consultarlos de forma interactiva para responder preguntas específicas. Especialistas, conocidos como Administradores de Bases de Datos (*Data Base Administrators, DBAs*), controlan la operación del DBMS y son responsables de la creación de nuevas bases de datos y de la definición de las estructuras de tablas utilizadas para almacenar los datos.

Una de las características más importantes del DBMS es su capacidad para proteger a las personas y programas que utilizan los datos de los detalles de su almacenamiento físico. Debido a que todo acceso a los datos almacenados se realiza a través del DBMS, una base de datos puede reestructurarse o trasladarse a una computadora diferente sin interrumpir los programas escritos para utilizarla. El DBMS regula el acceso a los datos almacenados, otorgando acceso únicamente a las tablas y registros para los cuales un usuario determinado ha sido autorizado.

En la actualidad, el personal informático corporativo suele concebir una base de datos como el contenido de un sistema de gestión de bases de datos. (De hecho, los dos conceptos están tan estrechamente asociados que los DBMS, como Oracle, a menudo se denominan simplemente "bases de datos", incluso por parte de especialistas en tecnologías de la información).

Históricamente, sin embargo, las dos ideas eran distintas. El concepto de base de datos se originó alrededor de 1960, aproximadamente diez años antes de que la idea de un DBMS adquiriera uso generalizado. El concepto de base de datos surgió entre los tecnólogos bien financiados de la Guerra Fría dedicados al comando y control militar, y por lo tanto se asoció con las tecnologías enormemente complejas y costosas de las aplicaciones informáticas en línea, en tiempo real e interactivas. A mediados de la década de 1960, este concepto había ingresado al discurso gerencial y se utilizaba para describir los enormes conjuntos de datos compartidos necesarios para construir un "sistema de información de gestión totalmente integrado" (*Management Information System, MIS*) que integrara todos los aspectos de la gestión de una gran corporación.

En el plano técnico, sin embargo, el DBMS evolucionó a partir de una clase más humilde de programas conocidos como "sistemas de gestión de archivos" (*file management systems*), creados dentro del mundo poco glamoroso del procesamiento de datos corporativos para simplificar la creación de programas destinados a la administración rutinaria. El sistema de gestión de bases de datos fusionó el concepto gerencial de la base de datos con la tecnología específica del sistema de gestión de archivos. Como muestra este artículo, en la práctica el DBMS funcionó bien como sistema técnico para ayudar a los programadores de aplicaciones, pero decepcionó como panacea gerencial. La mayoría de los primeros sistemas DBMS se utilizaron principalmente para aplicaciones rutinarias, no fueron consultados directamente por los gerentes y no respaldaron la integración de todos los datos corporativos. Además, si bien la base de datos corporativa se había concebido originalmente como un repositorio de toda la información gerencial importante, la tecnología real del DBMS solo admitía el tipo de registros regulares altamente estructurados con los que los sistemas anteriores de gestión de archivos habían demostrado competencia.

La historia del DBMS proporciona, por tanto, un ejemplo interesante del proceso mediante el cual tecnologías particulares con cualidades muy específicas y fortalezas y debilidades distintivas se promueven en cambio como soluciones universales. El mismo patrón se ha observado en numerosas ocasiones: en las primeras discusiones sobre la recuperación de información (*information retrieval*) como un problema que podía resolverse para el caso general, con la consagración de las computadoras como tecnologías de la información (*information technology*), y con intentos más recientes de comercializar sistemas para "almacenamiento de datos" (*data warehousing*), "minería de datos" (*data mining*) o "gestión del conocimiento" (*knowledge management*) como soluciones técnicas universalmente aplicables a las necesidades organizacionales. En todos estos casos, la aceptación de la idea de la información como una cantidad generalizada que puede almacenarse y procesarse mediante máquinas sirve para eludir la diferencia entre conceptos humanos o gerenciales muy amplios de información y las capacidades mucho más restringidas de sistemas automatizados específicos.

## 2. LA BASE DE DATOS Y EL SISTEMA DE INFORMACIÓN DE GESTIÓN

Durante la década de 1970, cuando los sistemas de gestión de bases de datos se promovieron por primera vez ante los gerentes corporativos, se comercializaron como los medios tecnológicos mediante los cuales toda la información computarizada de una empresa podía asimilarse en un único conjunto integrado de datos. Esta idea, sin embargo, no era nueva. De hecho, su discusión generalizada entre expertos sobre las aplicaciones gerenciales de las computadoras se remonta a finales de la década de 1950, varios años antes de que se utilizara el término "base de datos" (*data base*) en este contexto. Para comprender el concepto inicial de base de datos y su atractivo, debemos comenzar examinando el concepto de Sistema de Información de Gestión (*Management Information System, MIS*).

En marzo de 1960, un representante senior de Arthur D. Little, entonces la firma de consultoría de gestión más grande y de mayor trayectoria, se dirigió a sus colegas en una conferencia organizada por la American Management Association para discutir nuevas aplicaciones de la tecnología informática a los problemas de la administración corporativa [102]. Milton D. Stone estaba, al igual que muchos de sus compañeros ponentes, entusiasmado con el increíble potencial del Sistema de Información de Gestión, entonces un concepto muy nuevo y muy emocionante [48]. El MIS, un concepto presentado al público gerencial por primera vez solo un año después, ya estaba en camino de convertirse en el concepto más ampliamente discutido en el mundo de la computación corporativa de la década de 1960, promovido incansablemente por consultores, "hombres de sistemas" (*systems men*, especialistas corporativos en gestión administrativa), expertos en computación y fabricantes de computadoras. Sus defensores sugerían que el mejor uso de la computadora, el único que realmente explotaría su potencial, era construir un sistema automatizado enorme capaz de proporcionar a cada gerente de una corporación completa cada último dato necesario para el desempeño de sus funciones, de manera oportuna. Alcanzaría, como lo expresó Stone, "desde el presidente del directorio hasta el capataz" (*from board chairman to straw boss*), e incluiría capacidades sofisticadas de modelado y pronóstico, así como informes fácticos simples [102, página 17].

El procesamiento de datos (*data processing*) ya estaba bien establecido como el nombre dominante para la computación administrativa [47], pero los entusiastas del MIS sugerían que este enfoque conservador y evolutivo desperdiciaba el poder de la computadora en mera automatización de tareas clericales. El MIS pretendía retirar estas máquinas costosas y desconocidas de las manos demasiado pedantes del contador (quien sostenía "prejuicios nacidos de toda una vida de educación y práctica en el mundo de las hojas de análisis de líneas finas amarillas") y del antiguo supervisor de tarjetas perforadas o "técnico en procesamiento de datos", desestimado por Stone como un zángano que seguiría cualquier instrucción que se le colocara delante.

Estos conceptos tempranos, bastante vagos, de conjuntos de datos incorporaban el supuesto de que toda la información relevante, ya fuera interna o externa, pasada o futura, económica o humana, podía acomodarse dentro de una única estructura. La década de 1950 había presenciado una proliferación repentina de discusiones sobre la información en diversos campos. La teoría matemática de la comunicación digital de Shannon [98] fue adoptada como una metáfora poderosa dentro de la naciente metadisciplina de la cibernética. Los bibliotecarios especializados en campos científicos y técnicos comenzaron a denominarse a sí mismos científicos de la información (*information scientists*) [112], mientras que los investigadores que intentaban automatizar la búsqueda de registros comenzaron a llamar a este trabajo recuperación de información (*information retrieval*) [17, 76]. Reportes elogiosos en la revista *Fortune* informaron a los empresarios sobre el poder de la teoría de la información (*information theory*) [12] y de la recuperación de información [11]. En 1958, la combinación de computadoras, métodos de investigación de operaciones y simulación fue denominada por primera vez "tecnología de la información" (*information technology*) [62].

La información estaba en el aire, como una especie de solución universal a los diversos males de los negocios, la ciencia y el gobierno.

Fueron hombres como Stone quienes introdujeron por primera vez a los gerentes a la idea de la información como una entidad generalizada y abstracta, separada de los formularios, informes, archivos y memorandos en los que anteriormente se había encarnado. Stone reconoció que un MIS flexible y completo solo podía construirse si toda la masa de papeleo de una empresa podía computarizarse e integrarse "para producir un cuerpo interrelacionado de datos útiles, o información". Sugirió que "este cuerpo de datos, un auténtico 'cubo de hechos' (*veritable bucket of facts*), [era] la fuente en la que se introducen cucharones de búsqueda de información de diversos tamaños y formas en diferentes ubicaciones" [102, página 17]. Otros, trabajando con ideas similares, propusieron otras frases en los años siguientes. Otro consultor sugirió que la oficina del futuro giraría en torno a un "centro de datos" (*data hub*), definido como "una fuente central de información que puede servir como estación de consulta instantánea para ejecutivos que necesitan datos para tomar decisiones" [110]. Representantes de Shell Oil hablaron de la necesidad de un "banco de datos electrónico, o conjunto de información, del cual puedan extraerse informes de muchos tipos" [51, 60].³

Estos cubos, conjuntos y centros parecen metáforas curiosas y bastante poco útiles hoy en día, y de hecho aquellos que intentaron construirlos utilizando la tecnología de la década de 1960 estaban condenados a la decepción. En lugar de fluir suave y fácilmente hacia un océano de conocimiento, la información coagulaba desordenadamente alrededor de las pequeñas memorias, unidades de cinta y estructuras de archivos inflexibles de los primeros mainframes. Sin embargo, si podemos dar un paso atrás por un momento de la familiaridad de la frase "base de datos" (*data base*), desconocida en los círculos de procesamiento de datos cuando Stone habló, ¿no es una base de datos aún más extraña, aún más metafórica, que un conjunto, cubo, centro o banco? Estas metáforas sirven para construir una versión particular de la información, en la que la riqueza del significado social que estructura y respalda la información en sus manifestaciones más específicas (una lista de partes, un pronóstico de ventas, una carta de queja) ha sido despojada, dejando atrás una sustancia inerte que puede almacenarse, refinarse o canalizarse según sea necesario. Implicaba que un solo tipo de tecnología o experiencia, y por lo tanto un solo grupo de profesionales calificados, podía procesar información de cualquier tipo.

A finales de la década de 1960, sin embargo, "base de datos" (*data base*) era una expresión común en los círculos de computación corporativa, reemplazando en gran medida los centros, cubos y conjuntos en los que los datos se habían alojado retóricamente anteriormente. Este término fue importado del mundo de los sistemas militares de comando y control. Se originó en o antes de 1960, probablemente como parte de la famosa red de comando y control antiaéreo SAGE. SAGE [40] [56] fue mucho más complejo que cualquier otro proyecto informático de la década de 1950, y fue el primer sistema importante en funcionar en "tiempo real" (*real-time*) – respondiendo inmediatamente a las solicitudes de sus usuarios y a los informes de sus sensores. Como resultado, SAGE tenía que presentar una representación actualizada y coherente de los diversos bombarderos, cazas y bases a todos sus usuarios. La System Development Corporation [10], un grupo de la RAND Corporation escindido para desarrollar el software para SAGE, había adoptado el término "base de datos" (*data base*) para describir la colección compartida de datos sobre la cual se basaban todas estas vistas.

La información se consolidaba en la "computadora central" (no mostrada). SDC promovió activamente el concepto de base de datos para uso militar y empresarial. Su interés en sistemas de bases de datos de propósito general formaba parte de su intento de encontrar nuevos mercados para su experiencia única en la creación de sistemas interactivos a gran escala. Durante finales de la década de 1950 y principios de la de 1960, SDC poseía, con mucho, la mayor concentración mundial de programadores con experiencia en sistemas a gran escala y en tiempo real [94]. Prestó especial atención al área de moda de los sistemas informáticos de "tiempo compartido" (*time-sharing*), en los que una computadora era utilizada de forma interactiva por varias personas, cada una libre de ejecutar cualquier programa que requiriera. Debido a que las computadoras eran entonces grandes y costosas, el tiempo compartido prometía hacer realidad comercial, por primera vez, el uso interactivo de computadoras de propósito general por parte de no especialistas. SDC invirtió fuertemente en esta área [4], e identificó los "sistemas de bases de datos centrados en la computadora" (*computer-centered data base systems*) como una aplicación clave de los sistemas de tiempo compartido, organizando (en colaboración con agencias militares) dos simposios sobre el tema en 1964 y 1965 [104].

Los Simposios sobre Bases de Datos de SDC fueron cruciales para difundir el concepto de base de datos más allá del mundo de los contratistas militares en tiempo real.

Los aproximadamente 185 participantes en el segundo simposio incluían oficiales militares de alto rango, celebridades del procesamiento de datos empresariales, e investigadores corporativos y académicos. Al informar sobre el evento en *Datamation*, la revista comercial líder en computación empresarial, Robert V. Head observó que las bases de datos ya habían desencadenado el "mayor golpe único" de nueva jerga "desde la gran fiebre del oro del tiempo compartido de 1963", dejando a los usuarios potenciales "cabizbajos y desmoralizados". Concluyó preguntándose si era "posible que los usuarios, liderados por los militares, se rindan ante estos sistemas de bases de datos sin que se dispare un solo tiro de ira" [52, página 41]. Fue alrededor de esta época que el término "base de datos" (*data base*) hizo sus primeras apariciones en la discusión continua sobre los sistemas de información de gestión. En 1965, el profesor de contabilidad de Harvard John Dearden utilizaba el término "base de datos" para describir el conjunto verdaderamente importante de hechos y cifras corporativas que debían compartirse entre diferentes áreas dentro de una empresa [39]. Dentro de la literatura más técnica, apareció como un medio para agrupar información de diferentes archivos, de modo que cada dato se almacenara solo una vez. Su gran ventaja sería "permitir que las categorías de información se agreguen, eliminen, expandan y revisen de otra manera, sin rediseñar completamente el archivo o reprogramar las rutinas de recuperación" [99, página 4].

La idea de la base de datos como un conjunto físico de datos subyacente a un MIS recibió una declaración temprana, clara y altamente influyente por parte de Head, quien definió la base de datos como el nivel inferior de una estructura piramidal [53]. La base de datos agrupaba información de todos los sistemas operativos de la empresa, y sobre ella se erigían sistemas de informes y modelos para informar a los gerentes de nivel superior [48, 45-50]. La metáfora encajaba muy bien con la idea de una base de datos que respaldaba el resto del sistema de información. Esto eliminaba la necesidad de que los expertos en sistemas determinaran de antemano exactamente qué información requeriría cada gerente. En cambio, los gerentes podían interrogar la base de datos y recibir cualquier información que necesitaran. La base de datos a menudo se denominaba un "reservorio" de información [54, 61, 113, página 30].

El intento de SDC de impulsar el concepto de base de datos en el discurso civil funcionó bien. El término base de datos (*data base*) llevaba algunas asociaciones específicas, basadas en las características particulares de empresas como SDC y de los proyectos militares de comando y control. Una de estas asociaciones era con la idea de operación en tiempo real (*real-time operation*): la base de datos se actualizaría constantemente y, si fuera posible, automáticamente con información actual recopilada de diversas fuentes. También se asumía que, como en SAGE, una base de datos podía ser "interrogada" en tiempo real por sus usuarios, respondiendo preguntas de forma interactiva en segundos. Además, la base de datos sería compartida entre muchos programas diferentes, cada uno de los cuales utilizaría solo un subconjunto de la información general contenida en ella.

En contraste, los intentos de SDC de comercializar su propia tecnología como medio para lograr este objetivo no fueron ni de lejos tan exitosos. SDC había utilizado sus simposios sobre bases de datos para exhibir sus propios sistemas en línea [16], financiados con dinero militar, todos los cuales funcionaban en las computadoras especiales y enormemente costosas desarrolladas para SAGE [104]. El intento más ambicioso de SDC de comercializar la tecnología de bases de datos llegó con un sistema llamado CDMS (*Commercial Data Management System*, Sistema Comercial de Gestión de Datos), un derivado de un sistema anterior llamado TDMS (*Time-shared Data Management System*, Sistema de Gestión de Datos de Tiempo Compartido) desarrollado bajo contrato de ARPA (*Advanced Research Projects Agency*, Agencia de Proyectos de Investigación Avanzada) y sometido a uso de prueba en instalaciones militares. Estos sistemas tenían como objetivo permitir a los no programadores crear estructuras de bases de datos, cargar datos en ellas y luego emitir consultas y recuperar sus resultados en línea. Los intentos de vender el programa de computadora TDMS fracasaron porque era costoso, necesitaba una computadora potente exclusivamente para sí mismo y solo podía ejecutarse en el sistema operativo desarrollado a medida por SDC. Los intentos de alquilar el uso de CDMS a través de terminales conectadas a computadoras centralizadas fueron igualmente infructuosos [10, páginas 116-121, 101, 107].

A finales de la década de 1960, la muy discutida base de datos administrativa seguía siendo un sueño sin una vía tecnológica clara de cumplimiento. Estos primeros intentos de proporcionar a los gerentes acceso interactivo y en línea a datos almacenados en archivos informáticos adolecían de varios problemas. Estos incluían la naturaleza enormemente costosa de la tecnología, la falta de interés por parte de la mayoría de los gerentes y los problemas en gran medida no abordados de tomar datos de todos los sistemas operativos rutinarios (nómina, contabilidad, inventario, facturación, etc.) y de alguna manera integrarlos y hacerlos disponibles dentro de la base de datos.

## 3. SISTEMAS DE GESTIÓN DE ARCHIVOS Y PROCESAMIENTO DE DATOS

Además del concepto bastante mal definido de "base de datos" (*data base*), el otro ingrediente intelectual principal del Sistema de Gestión de Bases de Datos (*Data Base Management System, DBMS*), y la base tecnológica clave para los sistemas reales de gestión de bases de datos de la década de 1970, fue el "sistema de gestión de archivos" (*file management system*) (junto con su pariente cercano, el "generador de informes" o *report generator*).

Los sistemas de gestión de archivos tenían como objetivo reducir el costo de producir programas administrativos rutinarios y hacer que los programas terminados fueran más fáciles de cambiar y mantener. Los sistemas de generación de informes facilitaban la producción de informes impresos basados en criterios particulares. Estas ideas, a diferencia del concepto de base de datos en sí, eran indígenas al mundo del procesamiento de datos administrativos, donde habían evolucionado lentamente. Mientras que la base de datos reflejaba un enfoque en tecnología de "cielo azul" (*blue sky*), operación en línea, genio científico y gasto enorme, estos sistemas de gestión de archivos estaban inicialmente orientados hacia tareas clericales, eran utilizados y apreciados principalmente por programadores y supervisores de procesamiento de datos, carecían de características para uso interactivo o en línea y no costaban mucho. Más que sistemas gerenciales glamorosos, eran herramientas humildes pero altamente efectivas para técnicos informáticos.

La necesidad de tales herramientas se hizo evidente a mediados de la década de 1950, tan pronto como las computadoras se aplicaron por primera vez a tareas administrativas. Los usuarios pioneros de computadoras pronto descubrieron que las actividades aparentemente simples de procesamiento de datos clericales, del tipo menospreciado por los entusiastas del MIS, estaban lejos de ser triviales en la práctica. Los pioneros de finales de la década de 1950 y principios de la de 1960 desarrollaron muchas técnicas y enfoques nuevos mientras luchaban por contener los costos de programación y operación maximizando al mismo tiempo la flexibilidad.

Las técnicas utilizadas para almacenar datos en cinta se tomaron de los métodos existentes de tarjetas perforadas. De hecho, los conceptos de registros, archivos, campos, códigos especiales para marcar el inicio y el fin de archivos, y la "fusión" (*merging*) de información de un archivo a otro (todos aún omnipresentes en los sistemas informáticos actuales) tienen sus orígenes en los sistemas de tarjetas perforadas.⁴

La primera generación de instalaciones estadounidenses de procesamiento de datos gastó mucho más y tardó mucho más de lo esperado en poner sus máquinas en funcionamiento. Desde el famoso uso de General Electric en 1954 de una computadora Univac para automatizar el procesamiento de nóminas [81], los gerentes de procesamiento de datos se sorprendieron por la complejidad del trabajo de programación y los requisitos rígidos que la tecnología informática imponía en áreas como la entrada de datos y el manejo de casos especiales. Al igual que las máquinas de tarjetas perforadas que las precedieron, las primeras computadoras generalmente trabajaban en un registro a la vez. Las diminutas memorias internas de las primeras computadoras, junto con la naturaleza inflexible y serial del almacenamiento en cinta, significaban que un trabajo importante único, como la nómina, podía requerir que decenas de programas se ejecutaran uno tras otro, cada uno leyendo y escribiendo información desde varias cintas [47].

Los sistemas de gestión de archivos evolucionaron a partir de la reutilización de subrutinas escritas para manejar tareas de entrada y salida dentro de programas de aplicación. Los primeros programas informáticos incluían todas las instrucciones necesarias para especificar los detalles minuciosos de leer y escribir información desde cinta o disco, y se veían obligados a verificar regularmente si un registro particular ya había sido recuperado [69, 178-204]. Los programadores expertos dedicaban gran parte de su tiempo a elaborar rutinas para leer registros de cintas e imprimir líneas en papel, lidiando cada vez con los numerosos errores, problemas de sincronización, atascos de cinta, etc., que podían frustrar su tarea. Los grupos de programación pronto tuvieron la idea de producir un único conjunto de subrutinas bien escritas y reutilizables para manejar estas tareas. El código estándar se modificaba ligeramente para adaptarse a la situación particular y luego se insertaba en cada programa de aplicación. El cambio tecnológico también jugó un papel. Los programas de aplicación estaban estrechamente vinculados a configuraciones de hardware particulares: incluso cambiar la unidad de cinta utilizada para almacenamiento temporal requería un trabajo de edición considerable, mientras que adaptar un programa para hacer un uso eficiente de más memoria o unidades de cinta adicionales implicaba una reescritura fundamental. El problema se complicaba a medida que las empresas intentaban aprovechar los beneficios de la automatización utilizando la salida de una aplicación importante como entrada para otra, por ejemplo, vinculando su sistema de programación de producción con su sistema de control de inventarios, su sistema de cuentas por cobrar y su sistema de facturación. A medida que los fabricantes de computadoras comenzaron a incorporar capacidades más potentes en su hardware de procesamiento de datos, incluidos búferes y unidades de procesamiento auxiliares para suavizar el flujo de datos, la programación requerida para leer y escribir registros en cinta se volvió más compleja.

Como resultado, los fabricantes de computadoras comenzaron a suministrar a sus clientes funciones estándar para optimizar estas tareas [9, páginas 181-185]. Esto facilitó la creación de nuevos programas, pero poco ayudó con otros problemas.

Otro problema era la dificultad para extraer información de la computadora: mientras que las ejecuciones diarias, semanales o mensuales de diferentes partes de un sistema de nómina podían producir informes impresos voluminosos, la única forma de obtener un informe especial era escribir otro programa. Si un gerente necesitaba tabular datos de una manera diferente, o incluir solo un subconjunto de los registros originales en los cálculos, podía esperar a que un programador estuviera disponible o revisar el impreso contando registros manualmente.

A finales de la década de 1950, los equipos de procesamiento de datos más innovadores habían comenzado a abordar esto mediante la creación de programas de "generación de informes" (*report generation*), en los cuales los programadores ingresaban descripciones del resultado deseado y de la organización de los datos dentro de los "archivos maestros" relevantes, y eran recompensados con los informes deseados. El trabajo del equipo de General Electric en la Reserva Nuclear de Hanford [72, 73] en su IBM 702 (la primera computadora grande de IBM diseñada principalmente para uso administrativo) fue particularmente importante en el establecimiento de estas técnicas.

Los sistemas de gestión de archivos tuvieron su origen en el uso de técnicas similares para crear y actualizar archivos de datos, así como para recuperar información de ellos. Las áreas iniciales más importantes fueron rutinas generalizadas para ordenar datos en un orden particular (una operación muy importante, y una en la que las computadoras basadas en cinta eran muy malas en comparación con las máquinas anteriores de tarjetas perforadas) y realizar otras operaciones de mantenimiento rutinarias en archivos. Debido a que una aplicación importante podía contener decenas de programas pequeños, cada uno leyendo y escribiendo ciertos archivos, de otro modo podría requerir esfuerzos hercúleos por parte del personal de programación hacer algo tan simple como agregar un dígito extra al número de empleado. Al separar el código generalizado de manipulación de archivos de las descripciones estandarizadas del formato de registro utilizado en cada archivo, estos enfoques comenzaron a facilitar a los programadores la modificación de formatos de registro sin reescribir completamente los programas.

Tales rutinas fueron escritas por los equipos de programación que trabajaban dentro de empresas usuarias de computadoras. En los primeros días de la computación, era común que programas de sistema o utilitarios de este tipo se compartieran libremente, más notablemente a través del grupo de usuarios SHARE establecido para usuarios de computadoras IBM grandes [1]. Durante finales de la década de 1950, SHARE coordinó esfuerzos para desarrollar el sistema de generación de informes de General Electric en sistemas más potentes para el IBM 709 llamado 9PAC, y un proyecto relacionado para el IBM 704 llamado SURGE.⁵

Los sistemas de gestión de archivos también resultaron ser un nicho importante para la naciente industria independiente de paquetes de software. Mark IV, el producto más exitoso de la industria temprana de software independiente, era un sistema de gestión de archivos descendiente del software de informes producido para la Douglas Aircraft Company [43, 88, 89].

## 4. ALMACENAMIENTO DE ACCESO ALEATORIO

Estas técnicas de gestión de archivos eran muy útiles con el almacenamiento en cinta, pero cuando las empresas comenzaron a almacenar sus datos en unidades de disco, la complejidad adicional de programar el almacenamiento y la recuperación de datos de acceso aleatorio hizo que su uso fuera casi esencial. La unidad de disco se ofreció por primera vez como una opción estándar para la mayoría de los sistemas informáticos principales en 1962 [2, 100, 109], aunque había estado disponible en un puñado de sistemas IBM un poco antes. Mientras que la cinta había sido previamente la única forma de almacenar magnéticamente archivos de información razonablemente grandes, de repente fue posible almacenar hasta mil millones de caracteres de datos en las unidades de disco conectadas a una sola computadora IBM grande.

La tecnología de disco progresó rápidamente, y a mediados de la década de 1960 los discos eran opciones estándar en muchos de los "sistemas de tercera generación" recién anunciados, junto con sistemas operativos, memorias grandes, terminales remotos y otras características comercializadas como la clave para el desarrollo de aplicaciones en línea [91]. El almacenamiento en disco prometía acercar mucho más a la realidad el sueño del MIS de un sistema totalmente integrado. Un sistema de disco grande parecía ser el cubo físico en el que se podían colocar los hechos, y del cual podían verificarse, recuperarse y actualizarse mediante muchos programas de aplicación diferentes.

En el almacenamiento en cinta, los registros generalmente se ordenaban en un orden particular y se colocaban uno tras otro a lo largo de la cinta. Esta era una limitación fundamental, porque, al igual que con las cintas de video actuales, podría ser necesario rebobinar toda la cinta para llegar a un punto deseado. Los usuarios aún necesitarían mantener archivos en papel, o hojear grandes pilas de impresiones rutinarias, para obtener acceso rápido a un registro específico. Las unidades de disco, sin embargo, ofrecían almacenamiento de "acceso aleatorio" (*random access*), proporcionando acceso casi instantáneo a cualquier parte de un disco. Esto prometía permitir la recuperación rápida de datos específicos según sea necesario, facilitando mucho la creación de informes especiales o la construcción de sistemas empresariales en línea, como el célebre sistema de reservas de aerolíneas SABRE [34, 83]. El acceso aleatorio prometía una recuperación de registros casi instantánea, pero aunque era fácil ordenar a la computadora que leyera una parte particular de un disco (como unidad 4, plato 5, lado 1, pista 3, sector 15), no había una forma fácil de saltar directamente a un registro particular (por ejemplo, cuenta de cliente 15274). Uno podía, por supuesto, mantener los registros ordenados en orden, pero esto requeriría una enorme cantidad de trabajo reorganizando los registros existentes cada vez que se agregaba uno nuevo. Los programadores experimentaron con una variedad de estrategias para organizar e indexar datos en dispositivos de acceso aleatorio [69]. Ninguna técnica única era adecuada para todas las situaciones, y la mayoría de ellas eran muy complicadas de programar.

Otro conjunto de problemas fue causado por tener varios programas compartiendo un solo disco, cada uno utilizando código de programa diferente para leer y escribir registros. Entre estos problemas se encontraban el riesgo de que un programa errante pudiera desordenar un área del disco que contenía información perteneciente a otro, la sobrecarga impuesta por escribir varias versiones diferentes del código requerido para manejar técnicas de indexación complejas, y la certeza de que en algún momento el diseño físico del almacenamiento en disco cambiaría (por ejemplo, para trasladar un archivo en crecimiento a su propio disco y expandir las áreas de almacenamiento para los restantes) y todos los programas tendrían que modificarse a la vez.

La forma más obvia de lidiar con este enorme aumento en la complejidad era confiar en una nueva generación de sistemas de gestión de archivos generalizados construidos para trabajar con discos de acceso aleatorio [22, 24]. Estos sistemas tenían como objetivo acelerar el desarrollo de programas, reducir los costos de mantenimiento, proteger a los programas de aplicación de las consecuencias de los cambios en el diseño físico del disco y facilitar la recuperación selectiva de registros basándose en sus contenidos.

A finales de la década de 1960, cada fabricante importante de computadoras ofrecía al menos una pieza de software avanzado de gestión de archivos. Estos generalmente se basaban en la expansión de sistemas originalmente producidos para uso dentro de una sola organización. El más innovador e influyente de estos sistemas fue el Integrated Data Store (IDS, Almacén de Datos Integrado) de General Electric, creado por Charles W. Bachman. IDS comenzó su vida alrededor de 1963, como parte de un esfuerzo conocido internamente como "Integrated Systems Project II" (Proyecto de Sistemas Integrados II). Su objetivo era la producción de un sistema integrado para el control de producción, lo suficientemente flexible como para ser fácilmente personalizable por los muchos departamentos de GE, pero lo suficientemente potente como para dar resultados rápidos a consultas sobre programación de producción y niveles de inventario, mientras colocaba automáticamente pedidos y calculaba las cantidades óptimas de pedido.

El sistema resultante, MIACS (a veces, pero no siempre, *Manufacturing Information And Control System*, Sistema de Información y Control de Manufactura) dependía de IDS para manejar sus necesidades de almacenamiento y recuperación de datos. El proyecto estaba muy en línea con el impulso de principios de la década de 1960 para crear sistemas MIS integrados, y Bachman recuerda que se le dijo a la alta dirección que el nombre del proyecto significaba *Management Information And Control System* (Sistema de Información y Control de Gestión) [6].

La manufactura implica el ensamblaje de múltiples componentes en partes más grandes, que a su vez suelen servir como componentes en uno o más tipos de ensamblajes mayores. La necesidad de resolver este problema de "explosión de partes" (*parts explosion*) hizo que fuera particularmente importante para IDS apoyar la creación de vínculos entre diferentes tipos de registros. Mientras que los sistemas anteriores habían apoyado la idea de subregistros, almacenados secuencial y jerárquicamente dentro de registros maestros, IDS era mucho más flexible. Este concepto generalizado de vínculos entre tipos de registros, conocido más tarde como el "modelo de datos de red" (*network data model*), fue una influencia importante en las implementaciones tempranas de DBMS.⁶

IDS fue diseñado desde el principio para su uso con unidades de disco. Tomó el control de una computadora GE 225 completa, proporcionando funciones básicas de sistema operativo, incluida una implementación temprana de memoria virtual paginada para exprimir el máximo rendimiento de la memoria estándar de 8K del 225. El programador de tareas para la aplicación MIACS en sí dependía de IDS para almacenar datos. Los programas de aplicación MIACS (escritos en el lenguaje GECOM propio de General Electric) utilizaban instrucciones simples para navegar a través de las relaciones entre registros y para almacenar (*STORE*), obtener (*GET*), modificar (*MODIFY*) o eliminar (*DELETE*) registros uno a la vez. En la primera implementación de IDS, un preprocesador reemplazaba estas instrucciones especiales con las cadenas apropiadas de instrucciones de ensamblador. Sin embargo, las preocupaciones de eficiencia obligaron a cambiar a un enfoque diferente, donde IDS realizaba esta expansión de forma interpretativa, combinando la operación solicitada con metadatos sobre el tipo de registro involucrado. Esta parte de IDS permanecía residente en memoria, esperando atender las solicitudes de datos de los programas de aplicación [6].

Unos años más tarde, alrededor de 1965, la primera versión de lo que eventualmente se convertiría en el Information Management System (IMS, Sistema de Gestión de Información) de IBM fue producida por IBM en colaboración con North American Rockwell para manejar la proliferación de partes involucradas en el programa Apolo [13]. La versión original de esta aplicación, conocida como Generalized Update Access Method (Método Generalizado de Acceso de Actualización), funcionaba en una computadora IBM 7010 y utilizaba un sistema de gestión de archivos jerárquico especializado para almacenar sus datos en disco. IBM y NAA también desarrollaron un sistema llamado RATS (*Remote Access Terminal System*, Sistema de Terminal de Acceso Remoto) para que los programas de aplicación interactivos pudieran accederse a través de terminales. En 1966 comenzó el trabajo en una nueva versión creada para ejecutarse como una aplicación bajo OS/360 en las nuevas máquinas System 360, y fue esta versión la que IBM distribuyó a otros clientes a partir de 1968. Al igual que IDS, IMS era utilizado por programadores de aplicaciones, utilizando procedimientos empaquetados para incorporar capacidades de manejo de datos en su código. La versión OS/360 permitía que una copia residente en memoria de IMS atendiera simultáneamente las necesidades de datos de múltiples tareas de aplicación [26, 84].

General Electric ofreció una versión mejorada de IDS a los usuarios de sus computadoras, e IBM hizo lo mismo con IMS. Durante la década de 1960, los proveedores de computadoras "empaquetaban" (*bundled*) su software con hardware, utilizándolo como una herramienta promocional gratuita para atraer a los usuarios a comprar computadoras.

## 5. EL SISTEMA DE GESTIÓN DE BASES DE DATOS Y EL DBTG

La innovación tecnológica representada por sistemas como IDS fue paralela a desarrollos conceptuales. Hasta aproximadamente 1968, los conceptos de bases de datos y sistemas de gestión de archivos permanecieron en gran medida distintos. La base de datos se utilizaba de forma interactiva en línea, podía ser utilizada por no especialistas y estaba estrechamente asociada con el MIS y la idea de un único reservorio enorme de información corporativa. Los sistemas de gestión de archivos se utilizaban principalmente por programadores, para reducir los costos de desarrollo y mantenimiento de aplicaciones rutinarias de procesamiento de datos. Los sistemas de gestión de archivos más avanzados comenzaban a agregar características para facilitar la agrupación de información de múltiples archivos, y se estaban realizando esfuerzos para agregar acceso en línea [18].

La combinación de la base de datos y el sistema de gestión de archivos creó el Sistema de Gestión de Bases de Datos (*Data Base Management System, DBMS*). La idea del DBMS fue moldeada y promovida a través del trabajo de un organismo llamado Grupo de Trabajo sobre Bases de Datos (*Data Base Task Group, DBTG*), un comité *ad-hoc* del grupo de la industria informática CODASYL (*Committee On Data SYstems Languages*, Comité sobre Lenguajes de Sistemas de Datos). El enfoque de CODASYL era la creación de estándares de procesamiento de datos, y es más conocido por su trabajo diseñando y manteniendo el lenguaje de programación COBOL utilizado para la mayoría de la programación de aplicaciones empresariales desde finales de la década de 1960 hasta principios de la de 1990. El DBTG fue presidido por William Olle de RCA (entonces un fabricante de computadoras mainframe) y sus miembros fueron seleccionados entre proveedores de computadoras, universidades, empresas de consultoría y algunas grandes empresas que hacían un uso intensivo de computadoras en sus propias operaciones comerciales. Charles Bachman, el creador de IDS, fue un miembro temprano del comité y promovió las ideas que desarrolló para IDS como base para su trabajo.

Como su nombre sugiere, el DBMS tenía la intención de ser un nuevo tipo de producto, extendiendo las capacidades de los sistemas existentes de gestión de archivos para apoyar el tipo de capacidades avanzadas, en línea e interactivas y enormes almacenes de datos integrados asociados con el concepto de base de datos. Esto fue, en muchos aspectos, el punto final de una evolución natural. El DBTG estaba dominado por los mismos fabricantes que estaban agregando características a sus sistemas de gestión de archivos y habían comenzado a promoverlos como soporte, o incluso como, Sistemas de Información de Gestión (*Management Information Systems, MIS*) [108]. El propósito del DBTG era definir las capacidades de estos nuevos sistemas y desarrollar nuevos estándares para ellos. Su creación fue impulsada por la comprensión dentro de CODASYL de que COBOL, si bien hacía mucho para estandarizar el almacenamiento de datos en sistemas de cinta y para separar las definiciones de registros de la lógica del programa, era completamente inadecuado cuando se enfrentaba al desafío del almacenamiento basado en disco de acceso aleatorio [80]. En su formación en octubre de 1965, el DBTG había sido llamado originalmente el Grupo de Trabajo sobre Procesamiento de Listas (*List Processing Task Force*; su nombre fue cambiado solo en 1967).⁷

En 1969, el DBTG publicó su primer informe importante sobre lo que ahora denominaba "Sistemas de Gestión de Bases de Datos" (*Data Base Management Systems*). A pesar del cabildeo de empresas como General Electric para que sus propios sistemas fueran adoptados como base para un nuevo estándar, el grupo decidió que ningún sistema existente se acercaba a proporcionar la gama de características requeridas. En cambio, el grupo examinó las fortalezas y debilidades de los sistemas existentes y comenzó el intento de estandarizar características útiles. El trabajo continuó, en parte porque el comité principal del grupo de trabajo no estaba satisfecho con los resultados originales. En abril de 1971, se emitió un segundo informe importante y definitivo [30] y fue oficialmente respaldado por CODASYL.⁸

El trabajo del DBTG proporcionó tanto un esquema conceptual amplio para el sistema de gestión de bases de datos, como borradores de especificaciones detalladas para dos partes específicas del sistema general (un lenguaje de definición de datos para definir la estructura de la base de datos, y un lenguaje de manipulación de datos separado para acceder a los datos desde dentro de COBOL). También delineó una forma de dar a los programas individuales acceso a versiones selectivas o simplificadas de la base de datos completa.

Este marco conceptual para el DBMS finalmente resultó más influyente que las propuestas detalladas del DBTG. Cuando se menciona el trabajo de CODASYL hoy en día, generalmente es por la propagación del modelo de datos de red (*network data model*). Dado que IDS, un producto comercial, utilizó este modelo antes del establecimiento del DBTG, esto parecería una contribución bastante limitada a la historia. De hecho, el DBTG parece haber creado, o al menos haber definido públicamente por primera vez, la propia idea del sistema de gestión de bases de datos tal como lo conocemos hoy.

El DBTG proporcionó un nuevo vocabulario con el cual discutir estos problemas, incluida la separación del "lenguaje de definición de datos" (*data definition language*) utilizado para definir estructuras de bases de datos del "lenguaje de manipulación de datos" (*data manipulation language*) utilizado por los programadores de aplicaciones para trabajar con los datos en sí.⁹ Su contribución final fue insistir en que un DBMS estándar permitiera establecer vínculos más complejos entre diferentes archivos (o, como ahora se les llamaría, tipos de registros) dentro de la misma base de datos. El DBMS tenía la intención de hacer que estas relaciones (o, como las llamaba el DBTG, "conjuntos" o *sets*) fueran tan explícitas y aplicables como los sistemas anteriores de gestión de archivos habían hecho con la especificación de campos dentro de un archivo individual. Debido a que la mayor parte de la lógica para mantener estas relaciones había estado previamente oculta dentro de programas individuales, colocar las relaciones dentro del DBMS junto con los datos en sí garantizaba que todos los programas de aplicación y las solicitudes de usuarios tuvieran acceso a ellas. El DBTG también decidió que, si bien el enfoque jerárquico utilizado por sistemas como IMS era bueno para algunas cosas, resultaba indebidamente restrictivo cuando se aplicaba a otras. En cambio, especificó un modelo de "red" (*network*) para representar estas relaciones, permitiendo la creación de relaciones más complejas entre diferentes grupos de registros.

Aunque la mayoría de las características que el DBTG especificó para un DBMS ya habían sido demostradas por al menos un sistema de gestión de archivos o base de datos, insistió en que los sistemas futuros debían proporcionar todas ellas. Se esperaba que un DBMS proporcionara el acceso eficiente basado en lotes (*batch-based access*) para programadores y características de vinculación de registros en red en las que los sistemas existentes como IDS se especializaban. Sin embargo, también se esperaba que permitiera a los no programadores utilizar una interfaz simple y especialmente diseñada para consultar y actualizar la base de datos directamente, el ámbito de sistemas como Mark IV. Asimismo, se esperaba que el DBMS respaldara el uso interactivo en línea y la operación por lotes con igual facilidad [31].

El término Sistema de Gestión de Bases de Datos (*Data Base Management System*), casi desconocido antes de su adopción por el DBTG, se difundió rápidamente a partir de 1971. Se aplicó retroactivamente a algunos sistemas existentes y se utilizó para describir virtualmente cada nuevo sistema de gestión de archivos, independientemente de su fidelidad a las ideas específicas del DBTG. Esto acompañó una gran cantidad de publicidad, ya que una avalancha de libros de texto, artículos técnicos y piezas orientadas a la gerencia expusieron el potencial de la base de datos. Tras una transición traumática a equipos de tercera generación, muchas grandes corporaciones ahora ejecutaban computadoras potentes con unidades de disco grandes y sistemas operativos flexibles y multitarea, y comenzaban a experimentar con terminales en línea para el acceso a datos. Mientras tanto, el mercado recién establecido de software empaquetado producido de forma independiente estaba dominado por software de sistema, particularmente sistemas de gestión de archivos y sistemas de gestión de bases de datos [49]. Un artículo de 1973 en *Infosystems*, la publicación líder de procesamiento de datos orientada a la gerencia, aseguró a sus lectores que los sistemas de bases de datos eran como los esfuerzos aeronáuticos de los hermanos Wright: aunque los esfuerzos tempranos cuidadosamente planificados "nunca desarrollaron mucho sustentación cuando se aplicaron a las realidades prácticas de procesar archivos grandes que tenían que almacenarse, indexarse y ordenarse con datos en vivo", ahora estaban listos para elevarse majestuosamente al aire [93].

Un resultado inmediato y dramático del debut del concepto de DBMS fue un nuevo aumento del interés en la base de datos como fundamento de un sistema de información de gestión a nivel de toda la empresa. Durante finales de la década de 1960, una ráfaga de publicidad negativa basada en informes de retrasos y desastres entre los pioneros del MIS había comenzado a plantear dudas sobre su viabilidad práctica. El concepto de DBMS apareció como un salvador técnico para la idea del MIS como un sistema único y abarcador utilizado directamente por gerentes de todos los niveles, y figuró prominentemente en muchos artículos y libros de texto de principios y mediados de la década de 1970. Funcionó casi como un sinónimo de MIS. Richard Nolan, profesor de la Harvard Business School, consultor y uno de los escritores más prominentes sobre computadoras y gestión durante la década de 1970, utilizó un artículo de 1973 en la *Harvard Business Review* para definir la base de datos, de manera bastante audaz, como "un único conjunto o banco" donde "todos los datos legibles por computadora" se almacenan. Predijo que el uso tan esperado de computadoras por parte de altos ejecutivos finalmente estaba a la mano, "a partir de la unión del concepto de base de datos y el concepto de modelo corporativo..." [78, páginas 101 y 105]. Como observó al año siguiente, "si el término Base de Datos o DB se utiliza para reemplazar el término MIS, los títulos de artículos recientes son notablemente similares a los títulos de artículos de MIS de hace varios años" [79, página 27]. Muchos simplemente se habían aferrado a la base de datos como un nombre nuevo y más aceptable para este MIS "total".

Al igual que los conceptos de sistemas de información de gestión y de recuperación de información, la idea de una base de datos fue el producto intelectual de un movimiento social que intentaba construir un nuevo sentido de la información, como algo que podía procesarse, recuperarse y crearse utilizando nuevos cuerpos de técnicas científicas. Al igual que estos otros conceptos de información, la idea de una base de datos funcionaba en parte para definir una nueva área de autoridad profesional. Se aprecia una tensión considerable a principios de la década de 1970 entre aquellos que, ya sea por temperamento, experiencia práctica u orientación técnica, veían el DBMS como una herramienta práctica para mejorar la eficiencia de los programadores, y aquellos que adoptaban esta visión más utópica de la base de datos y hacían pocas menciones de sus fundamentos tecnológicos.

Como explicó uno de los libros de texto más orientados a la práctica sobre el tema [66, página 22], "Una idea muy publicitada pero impráctica de una base de datos dice que una corporación mantiene todos sus elementos de datos procesables en un gran reservorio en el que una diversidad de usuarios de datos pueden ir a pescar". La misma idea había recibido una declaración temprana por parte de Michael Scott Morton, fundador de un prominente grupo del MIT que investigaba las aplicaciones gerenciales de la tecnología informática, quien en 1971 sugirió que "la base de datos 'integrada' o 'a nivel de toda la empresa' [era] una noción engañosa, e incluso si pudiera lograrse, sería exorbitantemente costosa" [45].

Estas objeciones no detuvieron las cuentas esperanzadoras de la base de datos como una maravilla tecnológica que finalmente centralizaría y controlaría información de todo tipo, transformándola de una abstracción en una base de poder organizacional sólida. Este sueño quedó consagrado en una nueva figura: el Administrador de Base de Datos (*Data Base Administrator, DBA*). Según una de las descripciones más tempranas, el DBA debe "ser técnicamente calificado, si no inventivo... debe alentar a los usuarios a trabajar con él de buena gana y, sin embargo, se verá obligado a fallar en contra de sus proyectos favoritos; debe representar tanto a la gerencia como a los usuarios simultáneamente; debe ser todo para todas las personas en todo momento". El autor admitió que este rol "no existe como una función formalmente establecida en los negocios de hoy", pero consideró inminente su surgimiento [64, página 12]. Nolan fue aún más audaz: creía [79, 39] que el DBA sería responsable de "los datos como un recurso... mucho más amplio que solo los datos legibles por computadora", una vez que "la función de recurso de datos [hubiera sido] escindida de la función de gestión general". Un consultor [63, página 9] escribió que el DBA debería ser "algo así como una superestrella". La discusión sobre el DBA hace particularmente aparente la brecha entre utópicos orientados a la gerencia y pragmáticos orientados a los programadores. Schubert, quien en B.F. Goodrich había supervisado un proyecto de desarrollo de DBMS interno notablemente ambicioso, señaló simplemente [95, página 47] que "La administración de la base de datos es realizada por uno o más expertos técnicos que conocen el diseño y la creación de bases de datos, la operación del sistema de gestión de bases de datos y el uso de uno o más lenguajes de manipulación de datos. El administrador de la base de datos también debe ser capaz de trabajar bien con analistas de sistemas, programadores y personal de operaciones informáticas". Parece probable que esto reflejara la práctica en aquellas empresas que realmente utilizaban la tecnología en lugar de solo hablar de ella; ciertamente, para cuando la tecnología DBMS se volvió ubicua en la década de 1980, el DBA era un especialista técnico en lugar de un ejecutivo de información.

La idea del "diccionario de datos" (*data dictionary*) recibió una discusión considerable a principios de la década de 1970. Este era un registro central de la información recopilada y producida por diferentes partes del negocio. Al estandarizar diferentes representaciones de la misma información y establecer reglas claras sobre quién era responsable de cada pieza, las empresas podían eliminar la duplicación y sentar las bases para una mayor integración. Originalmente se veía como una herramienta gerencial, más que técnica: un consultor de Arthur D. Little señaló que "en su forma más simple, un diccionario de datos es un cuaderno bien organizado y actualizado que contiene información básica sobre elementos de datos" [36, página 102]. Pero, al igual que con el DBA, el diccionario de datos pasó de lo gerencial a lo técnico: después de que el término se aplicó a decenas de productos de software a finales de la década de 1970 [21], llegó simplemente a describir esa porción del DBMS donde se mantenían las definiciones del Lenguaje de Manipulación de Datos (*Data Manipulation Language, DML*).

Un defensor de IBM del enfoque del diccionario de datos [20, 23] comparó los datos con el dinero: "[u]na vez que la gerencia comprende la relación de los datos confiables con el bienestar corporativo, tratará sus datos con el mismo cuidado utilizado para manejar su efectivo". Nolan hizo una propuesta similar en su libro *Managing the Data Resource Function* (Gestión de la Función de Recurso de Datos), cuyo título sugería que la información, al igual que las personas y el dinero, era un recurso vital del negocio y, por lo tanto, merecía una atención gerencial similar [79]. De hecho, las afirmaciones hechas por Nolan de que el DBA sería encargado de la responsabilidad general de toda la información corporativa, utilizando tecnología informática cuando fuera apropiado pero reclamando finalmente autoridad gerencial más que técnica, prefiguran directamente las afirmaciones hechas más generalmente para la nueva posición de Director de Información o CIO (*Chief Information Officer*) en la década de 1980 [103].

## 6. SISTEMAS DBMS TEMPRANOS EN USO

El DBMS disfrutó de un éxito práctico considerable durante la década de 1970. A finales de la década, la mayoría de las instalaciones informáticas grandes habían instalado un paquete DBMS de algún tipo. Muchos de los productos financieramente más exitosos de la industria independiente de software eran paquetes de DBMS o de gestión de archivos. La adopción de software de gestión de bases de datos resultó ser una bendición para los programadores de aplicaciones. En aplicaciones administrativas del tipo tradicionalmente llevado a cabo por departamentos corporativos de procesamiento de datos, una enorme cantidad de tiempo de programador se dedicaba a hacer las cosas que los DBMS debían automatizar. Hicieron que los programas fueran más baratos de desarrollar, mucho más fáciles de mantener y facilitaron la integración de diferentes tareas empresariales. La tecnología de gestión de bases de datos tal como la definió el DBTG era muy buena para manejar datos muy uniformemente estructurados y jerárquicos del tipo que se encuentra en formularios administrativos.¹⁰

Sin embargo, el DBMS nunca llegó a cumplir completamente las expectativas de personas como Nolan, quienes lo veían como una panacea gerencial. De hecho, el bombo gerencial que se desarrolló en torno a la tecnología DBMS puede haber dificultado que las empresas tomaran decisiones técnicas informadas. Ya en 1973, un informe [35] de dos consultores de Booz, Allen & Hamilton sugirió que tanto el software como el hardware necesario seguían siendo inmaduros, que hasta entonces existía poca experiencia en su uso y que las características generalizadas ofrecidas por el DBMS traían una penalización de rendimiento considerable y bien podrían desencadenar la compra de más memoria o una nueva unidad de procesador. La mayoría de los costos reales estaban ocultos, particularmente los requisitos de personal. Como lo expresaron, "Algunos DBMS son tan complejos como el sistema operativo que los atiende. Además, este grupo debe aplicar y probar continuamente nuevas correcciones de programas y nuevas características para mantener el sistema 'vivo y en buen estado'. No es raro ver que un pequeño equipo de programación de sistemas se duplique o incluso triplique como resultado de un DBMS" [35, página 74].

Informes posteriores, en [97], sugieren que estos problemas continuaron durante varios años, y que muchas empresas instalaron paquetes DBMS debido a una "moda" (*bandwagon*) más que a una evaluación cuidadosa e informada. A pesar de que el acceso directo por parte de ejecutivos era una piedra angular teórica de la base de datos como herramienta de MIS, ninguna encuesta de principios de la década de 1970 pudo encontrar empresas donde la base de datos fuera utilizada directamente por gerentes, o incluso por analistas [78, página 113].

Las empresas deseosas de obtener un DBMS tenían que realizar esfuerzos considerables. Richard F. Schubert de la firma química B.F. Goodrich había sido parte del DBTG y llevó a su empresa a implementar su propio sistema IDMS basado en una versión simplificada de las propuestas de CODASYL. Se utilizó para respaldar aplicaciones en modo por lotes (*batch mode*), como facturación y contabilidad, así como acceso en línea para entrada de pedidos y su inventario de productos terminados [57]. En 1973, Goodrich vendió los derechos de IDMS al emprendedor con visión comercial John Cullinane, quien para principios de la década de 1980 había construido una firma de software epónima, una de las más grandes y de más rápido crecimiento de la época, en torno a él [68, 242-246]. Pocas empresas estaban dispuestas a llegar tan lejos para obtener un DBMS, y de hecho, los expertos de principios de la década de 1970 coincidieron en que la naturaleza excepcionalmente compleja y generalizada de las tecnologías involucradas hacía que la selección de un buen paquete fuera mucho más sensata que intentar desarrollar un sistema internamente.

Incluso entre las empresas que adquirían los paquetes DBMS más avanzados, el uso en línea era limitado y las aplicaciones gerenciales eran raras. Consideremos dos ejemplos de empresas que utilizaban DBMS suministrados comercialmente a principios de la década de 1970. McDonnell Douglas, utilizando el sistema IMS de IBM, afirmó haber creado una base de datos centralizada que contenía toda la información previamente almacenada en 264 archivos que cubrían aspectos como repuestos, programación de producción, manejo de listas de materiales y gestión de inventarios. Esto facilitó mucho cambiar los 95 programas existentes que dependían de estos archivos, y establecer referencias cruzadas automáticas entre diferentes registros y, se esperaba, avanzar hacia la operación en línea en el futuro [55]. La segunda empresa, mucho más pequeña, se dedicaba al procesamiento de cuentas por cobrar para médicos. Utilizó un DBMS influenciado por el DBTG en su computadora Xerox para reducir sus tiempos de procesamiento diario para actualizaciones y diseñar su nuevo programa más rápidamente. Los resultados la complacieron, a pesar del hecho de que el DBMS consumía una gran parte de la memoria de la computadora y utilizaba diez veces más capacidad de procesador que la versión basada en cinta. Había avanzado cautelosamente hacia la operación en línea: mientras que los registros se recuperaban utilizando terminales, todas las actualizaciones se ponían en cola y se aplicaban por la noche mientras el sistema estaba fuera de línea, con la creencia de que esto "reduce en gran medida la posibilidad de una pérdida catastrófica de datos" [14, página 63].

Según una encuesta de 1975 de grandes empresas industriales [90], aproximadamente un tercio utilizaba algún tipo de sistema avanzado de gestión de archivos o bases de datos. De ese tercio, alrededor de la mitad utilizaba sistemas destinados a consultas directas *ad-hoc* por parte de no programadores, como MARK/IV, y la otra mitad utilizaba sistemas diseñados para integrarse con los lenguajes de programación convencionales, como COBOL. Los sistemas híbridos, del tipo envisioned por CODASYL, aún no habían tenido mucho impacto. Solo alrededor de un cuarto de los sistemas se utilizaban principalmente para acceso en línea, y solo dos empresas afirmaron haber implementado una base de datos para toda la empresa, aunque la mayoría informó utilizarla para múltiples áreas del negocio.

Esto cambió muy lentamente. Cinco años más tarde, una encuesta de sistemas de información de gestión en treinta y dos grandes corporaciones encontró que la mayoría de estas empresas ahora habían instalado potentes paquetes DBMS [27]. Sin embargo, cuando los investigadores observaron el uso real que se hacía de estos sistemas, encontraron que: "Los usuarios encuestados solo estaban comenzando a desarrollar aplicaciones de DBMS.... Esto posiblemente se deba a las dificultades involucradas en desarrollar y controlar tales actividades" [27, página 28].

Incluso los productos diseñados explícitamente para uso por parte de no especialistas encontraron que sus principales mercados estaban entre los especialistas en procesamiento de datos. Debido a que costaban menos y podían ejecutarse en hardware más modesto, los sistemas de gestión de archivos siguieron siendo más ampliamente utilizados que los DBMS completamente desarrollados. La encuesta de 1975 de Powers encontró que el 41% de las empresas que utilizaban estos paquetes informaron que la información solo podía recuperarse con la ayuda de un programador. A diferencia de los sistemas más potentes diseñados principalmente para que los utilizaran los programadores de aplicaciones, estos sistemas todavía se utilizaban principalmente (en el 77% de las empresas) con archivos almacenados en cinta en lugar de en disco. Estos sistemas todavía trabajaban con archivos individuales en lugar de vastas bases de datos integradas; de hecho, el 55% de sus usuarios ni siquiera habían comenzado a integrar archivos para eliminar información redundante.

Durante la década de 1970, el sistema de gestión de archivos MARK IV se convirtió en el producto individual más exitoso en la admittedly corta historia de la industria: el primero en alcanzar los hitos de 1 millón de dólares, 10 millones de dólares y 100 millones de dólares en ventas acumuladas. En comparación con las propuestas del DBTG, sus capacidades eran modestas. Su atractivo inicial era directo: primero, era altamente eficiente en operación por lotes (*batch operation*), y segundo, había sido diseñado para uso por parte de no programadores. Las solicitudes de datos se ingresaban en uno de cuatro formularios de papel simples, y luego se perforaban en forma informática para su posterior procesamiento. Pero incluso MARK IV encontró su público principal entre los programadores. A medida que pasaba el tiempo, el desarrollo de MARK IV se centró cada vez más en las necesidades de programadores de tiempo completo, quienes lo utilizaban como base para la construcción de programas de aplicación complejos. Una historia oficial de la empresa atribuyó este proceso a la afluencia de especialistas en procesamiento de datos a su grupo de usuarios "IV League", lo que aseguró que sus opiniones "sobrepasaran las voces de los usuarios finales no programadores" en la planificación de la empresa [43, página 9.26]. Las actas de este grupo sugieren que los no especialistas encontraron el trabajo avanzado más difícil de lo que se había esperado. Según un representante de Eastern Airline, si bien la mayoría de sus 200 usuarios eran "una raza completamente nueva de codificadores... no programadores, con poca o ninguna experiencia en procesamiento de datos", los intentos de capacitarlos en técnicas de recuperación de información sin darles una comprensión de lo que ocurría en "la misteriosa caja negra" de la computadora habían fracasado. Contrario a sus expectativas, "Los únicos usuarios capaces de avanzar hacia capacidades extendidas con algún grado de éxito fueron aquellos con cierta experiencia en procesamiento de datos" [65, Apéndice F].

Si bien existía una demanda sustancial de productos que permitieran a los no especialistas producir informes computarizados sin la asistencia de programadores, los principales sistemas DBMS no hicieron un buen trabajo para satisfacer esta necesidad. Uno de los productos de software más exitosos de la década de 1970, Easytrieve de Pansophic, era un sistema de generación de informes fácil de usar diseñado para extraer información de archivos y bases de datos. Easytrieve prosperó en competencia con software más complejo de DBMS y gestión de archivos, y muchas empresas adquirieron los módulos opcionales necesarios para utilizarlo junto con los DBMS más potentes [87].

A finales de la década de 1970, entonces, estaba claro que la tecnología DBMS no había cumplido con las esperanzas depositadas en ella por sus promotores más orientados a la gerencia. Si bien los sistemas DBMS potentes eran ahora comunes en grandes corporaciones, pocos se utilizaban para respaldar nuevos tipos de aplicaciones gerenciales. Incluso los sistemas DBMS más sofisticados se utilizaban principalmente en modo por lotes (*batch mode*) en lugar de en línea, y por programadores más que por gerentes. El sistema de gestión de bases de datos era más un sistema mejorado de gestión de archivos. Los almacenes de datos masivos e integrados seguían siendo muy difíciles de construir, mientras que los modelos informáticos interactivos del tipo anticipado por los defensores del MIS seguían siendo notablemente ausentes.

## 7. EL SISTEMA DE GESTIÓN DE BASES DE DATOS DESDE 1980

En 1973, Charles W. Bachman recibió la Medalla Turing de la Association for Computing Machinery (Asociación para la Maquinaria Computacional), el premio más prestigioso en ciencias de la computación. La citación destacaba su creación del sistema pionero IDS (que retroactivamente denominó un DBMS) y su trabajo en el DBTG para incorporar estas ideas en sus especificaciones. Este premio fue en sí mismo un evento importante, que representaba un nuevo nivel de aceptación entre los investigadores en ciencias de la computación de los problemas de bases de datos como temas de investigación intelectualmente respetables, junto con áreas mejor establecidas como el análisis numérico, la teoría de compiladores y la teoría de algoritmos.

El evento es mejor recordado, sin embargo, por el discurso de Bachman [7]. Titulado "El Programador Como Navegante" (*The Programmer As Navigator*), desarrolló la idea de que el cambio a la tecnología DBMS representaba algo similar a la revolución copernicana, en el sentido de que el trabajo de los programadores ahora giraría en torno a la base de datos más que al hardware de la computadora. Aunque esta profecía tardó varias décadas en hacerse realidad, el conocimiento de los sistemas de bases de datos se ha convertido ahora en un requisito fundamental para prácticamente todo el trabajo de programación de aplicaciones administrativas, análisis de sistemas y diseño web avanzado. Pero, como también implicaba su título, el impacto de los DBMS generalizados sería mucho mayor para los programadores que para los gerentes.

La aceptación del concepto de sistema de gestión de bases de datos del DBTG implicó, por tanto, una visión nueva y más concreta de lo que era una base de datos: básicamente, un cuerpo de datos electrónicos que podía ser gestionado por un sistema de gestión de bases de datos. Como tal, el éxito comercial de los paquetes DBMS respaldó el creciente prestigio del personal informático corporativo, frente a los intentos de científicos de la información y documentalistas [5] de convertir a la biblioteca, más que a la sala de computación, en el corazón de cualquier sistema de información corporativo. A pesar de las esperanzas influenciadas por el MIS de la década de 1970 de que un DBMS podría ser el corazón de un sistema que incluyera toda la información corporativa, demostró ser competente para manejar solo un pequeño subconjunto de este material. La base de datos, tal como se realizó a través de una extensión de herramientas existentes de procesamiento de archivos, encarnaba la visión altamente estructurada y orientada a transacciones administrativas de la información sostenida por el personal de procesamiento de datos y los proveedores de computadoras.

El estrechamiento del concepto de base de datos y su estrecha asociación con el DBMS también representó un alejamiento de la idea, implícita en discusiones mucho más tempranas sobre recuperación de información, de que toda la información importante era científica o al menos era susceptible a las mismas técnicas de recuperación que la información científica. Los conceptos de base de datos pioneros de sistemas militares elaborados de la década de 1960, como el TDMS de SDC – acceso en línea, datos estructuralmente flexibles, definición interactiva de formatos de datos por parte de usuarios – jugaron un papel menor en los principales sistemas comerciales de la década de 1970. Tampoco existía un mercado comercial significativo para productos basados en estas tecnologías. Aunque los presupuestos de investigación industrial de las principales corporaciones podrían haber pagado suscripciones a las bases de datos científicas en línea recién disponibles de la década de 1970 [46], los gerentes y departamentos de computación de las mismas empresas tenían poco interés en utilizar estas tecnologías para gestionar su propia información. El surgimiento comercial de servicios de información en línea, discutido con gran detalle en [16], parece haber ocurrido en casi completo aislamiento del trabajo en paquetes DBMS.

El concepto de DBMS resultó ser mucho más importante y duradero que los métodos particulares para su realización propuestos por el DBTG de CODASYL. Durante la década de 1970, un nuevo enfoque, el modelo relacional (*relational model*) [25, 33], ganó gradualmente aceptación entre los investigadores de bases de datos. El modelo relacional era conceptualmente mucho más elegante y flexible que el modelo de red (*network model*) respaldado por CODASYL, que resultó ser tanto restrictivo (porque las relaciones debían especificarse cuando se diseñaba la base de datos) como insuficientemente abstraído del almacenamiento físico de los datos (los programadores todavía se veían obligados a escribir código para navegar explícitamente de un registro a otro cuando trabajaban con datos vinculados).

Debido a que el modelo relacional desplazó la responsabilidad de especificar relaciones entre tablas de la persona que las diseñaba a la persona que las consultaba, permitió que las tablas se unieran de diferentes maneras para diferentes propósitos. Esto resultó ser necesario (aunque no suficiente) para el establecimiento de bases de datos grandes y de propósito general compartidas entre diferentes departamentos y sistemas informáticos. El modelo relacional también ha sido elogiado por su naturaleza no procedural – separando aún más al usuario de los mecanismos de almacenamiento físico involucrados [75]. Esto simplificó la programación y aisló el código de aplicación de los cambios en la estructura de la base de datos. Al aceptar su propio premio Turing en 1981 por su desarrollo del modelo de base de datos relacional, Edgar F. Codd sugirió que el modelo de red de CODASYL había obligado al programador a convertirse en demasiado navegante, en un nivel lógico demasiado bajo [32].

El uso de los primeros sistemas DBMS estaba altamente concentrado. Según informes internos preparados por una firma de software, tan tarde como 1981, TOTAL, el líder del mercado, tenía solo 4.171 instalaciones, mientras que el IMS de IBM ocupó el segundo lugar con un estimado de 1.500 [82]. El primer DBMS relacional ampliamente utilizado, Oracle, se lanzó en 1980 y encontró un nicho temprano en el mercado en rápido crecimiento de sistemas de minicomputadoras. Durante la década de 1990, los sistemas relacionales ganaron el poder y la madurez necesarios para desplazar gradualmente productos anteriores de mainframe como IMS, aunque incluso hoy la transición está lejos de completarse. Al mismo tiempo, el creciente poder de los sistemas de computadoras personales abrió nuevos nichos para la tecnología DBMS en computadoras de escritorio y servidores departamentales económicos. Casi todas las aplicaciones empresariales personalizadas producidas durante la última década dependen de un DBMS relacional para almacenar y recuperar datos. Los sistemas DBMS relacionales se utilizan ampliamente en computadoras personales. De hecho, Microsoft ahora incluye una versión de su potente DBMS SQL Server con las ediciones "profesionales" de su suite Office, e incluso lo ha adaptado para su uso con sus computadoras de mano Pocket PC. Microsoft ha apuntado durante mucho tiempo, aunque hasta ahora sin éxito, a reemplazar el sistema de archivos convencional y los repositorios de correo electrónico que se encuentran en los sistemas operativos Windows actuales con un DBMS multitarea. En cierto sentido, el DBMS se ha convertido efectivamente en un contenedor universal para datos informáticos.

## 8. CONCLUSIONES

El sistema de gestión de bases de datos proporciona un ejemplo interesante de las tensiones ocultas detrás de frases como "tecnología de la información" (*information technology*). La progresión de los conceptos de base de datos y sistema de gestión de bases de datos a lo largo de las décadas de 1960 y 1970 demuestra una tensión inconfundible entre los logros bastante limitados y técnicamente enfocados de los sistemas de información reales y las afirmaciones universales, casi utópicas, de que los problemas de información pueden definirse y, por lo tanto, resolverse para el caso general si solo se pueden desplegar las herramientas o tecnologías adecuadas. Las tecnologías del sistema de gestión de archivos, por mucho que se hayan mejorado, nunca pudieron realizar los grandes sueños planteados para las bases de datos corporativas como fuentes universales de información. Si bien la invención del concepto de DBMS revivió inicialmente las esperanzas de creación de bases de datos todopoderosas, a largo plazo su efecto fue redefinir el propio concepto de una base de datos (o como ahora decimos, *database*) como el contenido de un DBMS.

A pesar de su notable ubicuidad, los DBMS basados en el modelo relacional continuaron incorporando los mismos supuestos sobre la información que los sistemas anteriores de gestión de archivos. En particular, la complejidad de la construcción de consultas relacionales significaba que para consultar y actualizar la base de datos aún se requería la participación de un programador, un programa de aplicación especialmente escrito o un especialista capacitado. Los diseñadores del ahora estándar lenguaje SQL (*Structured Query Language*, Lenguaje de Consulta Estructurado) habían asumido que reemplazar caracteres algebraicos con palabras como "SELECT" (SELECCIONAR) facilitaría a los gerentes escribir sus propias consultas [74], pero la complejidad y el rigor no podían eliminarse tan fácilmente. Y aunque el modelo relacional facilitó la unión de tablas de diferentes maneras, los diseñadores de bases de datos todavía tenían que especificar el formato exacto de cada columna dentro de la tabla e incluir exactamente los mismos campos en cada fila.

Como resultado, el DBMS era muy adecuado para los registros burocráticos de aspectos como la administración de nóminas, porque cada registro incluía las mismas piezas de datos (años de servicio, número de seguro social, tarifa por hora, estado de horas extras, etc.). Hizo que fuera muy simple y eficiente actualizar información, y por lo tanto es adecuado para sistemas administrativos donde los registros se actualizan constantemente. Por otro lado, era completamente inútil para representar y buscar datos con formato menos rígido, como registros de texto completo, correspondencia o incluso resúmenes científicos. Ciertamente, no ha habido escasez de interés por parte de los investigadores de bases de datos en el diseño de modelos alternativos y más flexibles. Muchos de estos se han promovido en productos comerciales, incluidos sistemas de bases de datos orientados a objetos (*object oriented database systems*) [114], bases de datos multivaluadas y otros enfoques. De hecho, "post-relacional" (*post relational*) se ha convertido en una palabra de moda de marketing durante la última década, y al igual que "relacional" en la década de 1980, y de hecho "sistema de gestión de bases de datos" en la década de 1970, se ha aplicado a una gama tan amplia de productos que ha difuminado completamente su significado real [37].

El punto sigue siendo, sin embargo, que la tecnología dominante de bases de datos de hoy todavía incluye conceptos rígidos de campos y tipos de datos heredados de los sistemas de tarjetas perforadas y sigue estando lejos de cumplir con la visión de un repositorio universal para datos de todo tipo. Solo con el auge de la World Wide Web a mediados de la década de 1990 la atención generalizada volvió al indexado y gestión de grandes cantidades de información en lenguaje natural. Sistemas como AltaVista y, más recientemente, Google han demostrado ser notablemente hábiles para devolver resultados relevantes de un mar de datos no estructurados. Sin embargo, estas tecnologías siguen siendo bastante distintas de los sistemas DBMS convencionales.

A medida que el uso de DBMS se proliferó, las empresas se encontraron incapaces de integrar todos los datos corporativos en un único conjunto de la manera prometida por los defensores tempranos de las bases de datos. Cuando la tecnología DBMS logró un uso casi universal, las grandes empresas se quedaron con cientos o miles de bases de datos desconectadas y duplicadas, sin una forma fácil de fusionarlas. El almacenamiento de datos (*data warehousing*), una de las obsesiones principales de los departamentos de TI corporativos y las firmas de consultoría de mediados y finales de la década de 1990, fue un intento de construir enormes bases de datos de solo lectura para fines de informes en las que todos los datos estuvieran vinculados y reformateados en una forma estándar. Las empresas pretendían utilizar estos cubos de hechos para "minería de datos" (*data mining*) y la provisión de "inteligencia empresarial" (*business intelligence*) para superar a sus competidores [38]. Los conjuntos de datos corporativos imaginados hace cuarenta años se han acercado cada vez más a la realidad, pero la desordenada realidad de tecnologías de almacenamiento de datos especializadas, limitadas e inflexibles sigue contrastando con la simplicidad prístina de la visión original.

⁴ Para la década de 1940, la mayoría de las tarjetas perforadas incluían 80 columnas de datos, cada una de las cuales codificaba un único número o letra. La información dentro de cada tarjeta se agrupaba en campos, cada uno ocupando un ancho fijo dentro de cada tarjeta de registro. Considere una fábrica que utiliza tarjetas perforadas para procesar su nómina [67]. Algunos campos necesitaban solo una columna – por ejemplo, sexo (M o F). Otros campos, como el apellido, podían asignarse a una docena de columnas. Cada registro se perforaría en una, o en algunos casos varias, de las tarjetas en la baraja. La baraja completa que representa a todos los trabajadores de la fábrica se conocía como un archivo, por analogía con los registros convencionales en papel. Cada tarjeta de registro dentro del archivo debía seguir exactamente el mismo diseño de campos, y para procesar un trabajo particular, los operadores de la máquina debían recablear el panel de control de cada máquina (como clasificadora, clasificadora-colacionadora o tabuladora) para reflejar este diseño específico de campos. (Muchos trabajos implicaban "fusionar" información de varios archivos – por ejemplo, combinar información salarial del "archivo maestro" de tarjetas de personal con la información de asistencia perforada en una tarjeta perforada semanal por un reloj de tiempo IBM). Los conceptos de archivo, registro y campo se transfirieron directamente al almacenamiento en cinta, aunque los registros ahora se disponían secuencialmente a lo largo de la tira de cinta magnética. Se introdujeron códigos adicionales para marcar el inicio y el fin de archivos y proporcionar verificaciones contra datos corruptos.

⁵ Según Charles W. Bachman, el proyecto SURGE de SHARE comenzó como un intento de modificar el Generador de Informes de Hanford para su uso con el IBM 704, pero eventualmente tomó una dirección diferente. El sistema 9PAC para el IBM 709, sin embargo, fue producido por un comité diferente de SHARE y parece haber sido ampliamente utilizado. Aunque 9PAC se utilizó exclusivamente con almacenamiento en cinta, permitía la creación de relaciones jerárquicas entre registros. Los registros hijos simplemente se almacenaban en cinta inmediatamente después de sus registros padres. Las definiciones de datos para el archivo se almacenaban en un encabezado [6]. El proyecto incluía un Generador de Informes y un sistema de Mantenimiento de Archivos Generalizado, cuyos creadores pretendían incorporar capacidades para actualizaciones calculadas y modificaciones al formato de archivos existentes. Las especificaciones para este último se encuentran en [70]. Su estructura de archivo compartida se describe en [71]. La serie de Distribuciones Secretariales de SHARE enviadas a todos los sitios de IBM 709 incluye mucha discusión sobre el proyecto, incluyendo una serie de borradores de documentación, solicitudes de información, comentarios y sugerencias. El Subcomité 9PAC del Comité de Procesamiento de Datos de SHARE se formó a finales de mayo o principios de junio de 1959.

⁶ IDS a menudo se denomina, y con cierta justificación, el primer sistema de gestión de bases de datos. En el plano técnico, estaba años por delante de su tiempo y fue pionero en muchas técnicas importantes. Sin embargo, por potente que fuera, la versión inicial de IDS carecía de algunas de las características asociadas con sistemas posteriores y formalizadas en la definición de DBMS de CODASYL. Las definiciones de registros se perforaban directamente en tarjetas en un formato especial en lugar de definirse y modificarse mediante un lenguaje de definición de datos. No proporcionaba una interfaz para consultas *ad-hoc*, ni soporte para acceso en línea, ya que fue creado puramente para respaldar la aplicación MIACS. No proporcionaba diferentes vistas o subconjuntos de la base de datos general a diferentes usuarios. Tampoco admitía múltiples bases de datos simultáneamente. Igual de importante, nadie en ese momento lo llamaba sistema de gestión de bases de datos. Ese concepto en sí no existía en ese momento.

⁷ La frase "sistema de gestión de bases de datos" (*data base management system*) se utilizó al menos una vez antes del cambio de nombre del DBTG, para describir el próximo Sistema de Información Generalizado (*Generalized Information System, GIS*) de IBM [18].

⁸ Las propuestas específicas fueron controvertidas en ese momento, y varios miembros de CODASYL se opusieron a ellas (incluidos los proveedores de mainframes IBM, RCA y Burroughs) [50]. Los grupos de usuarios de IBM SHARE y GUIDE llegaron incluso a producir un informe rival propio [23]. Los estándares de CODASYL para los lenguajes de DBMS no tuvieron tanto éxito como su trabajo en COBOL, en el sentido de que nunca se produjo una implementación completa de la especificación. Las extensiones a COBOL fueron reelaboradas por un nuevo comité permanente en forma de "Diario de Desarrollo" como un estándar oficial, publicado como [28]. El trabajo en estos estándares continuó hasta la década de 1980, primero a través de un nuevo comité establecido dentro de CODASYL, y más tarde en ANSI. Esto incluyó un DML para FORTRAN, para complementar el DML para COBOL en los informes anteriores [29]. Pero estos esfuerzos por estandarizar un lenguaje de definición de datos (*Data Definition Language, DDL*) no lograron establecer un estándar en el mercado, en parte debido a la renuencia de IBM a comprometerse con los conceptos de red inherentes al modelo de CODASYL mientras su producto estrella IMS mantenía un enfoque jerárquico [85]. Sin embargo, la mayoría de los sistemas avanzados entonces en desarrollo fueron influenciados en mayor o menor medida por las ideas de los informes de CODASYL; para un buen resumen de los sistemas comerciales más avanzados de mediados de la década de 1970, véase [42, 44].

⁹ El DBTG estandarizó términos como "registro" (*record*), "conjunto" (*set*) y "base de datos" (*data base*), y agregó algunos nuevos, incluido "esquema" (*schema*) (que sigue siendo omnipresente hoy en día) para describir el formato lógico de los datos dentro de la base de datos, y "subesquema" (*sub-schema*). Un subesquema (similar a lo que se llamaría una vista en los sistemas relacionales actuales) permitía a diferentes usuarios y aplicaciones ver solo una porción de la base de datos general, permitiendo acceso selectivo a registros y potencialmente protegiendo la aplicación de cambios en el esquema subyacente, una propiedad denominada "independencia de datos" (*data independence*). El DBTG también separó el Lenguaje de Manipulación de Datos (*Data Manipulation Language, DML*) utilizado para agregar, eliminar, actualizar y recuperar registros particulares del Lenguaje de Definición de Datos (*Data Definition Language, DDL*) utilizado para definir la estructura lógica de la base de datos en sí. Mientras que el DDL debía ser un lenguaje nuevo y universalmente aplicable, el DML tomó la forma de un conjunto de adiciones integradas perfectamente en un lenguaje de programación existente.

¹⁰ Al igual que los sistemas de gestión de archivos anteriores, los nuevos sistemas aún exigían que cada registro en un archivo (o "tipo de registro") incluyera exactamente los mismos campos, cada uno poblado con datos en exactamente el mismo formato. Además, debido a que las relaciones (o "conjuntos") se especificaban en el Lenguaje de Definición de Datos y, por lo tanto, se incorporaban a la base de datos, el diseñador de la base de datos se veía obligado a especificar un conjunto completo y coherente de vínculos entre diferentes archivos, algo que resultó esencialmente imposible de hacer para el tipo de bases de datos a gran escala, completas y multifuncionales envisioned por los proponentes del MIS.
